05 · Founder stage · 8 min

Founder stories : du prototype au revenu.

Le cœur du format Extended : founders qui racontent les bets early-stage qui ont payé, et les judgement calls qu'ils ont dû faire sans manuel.

Pattern 1 · Evals dès J1, pas après le PMF

Tous les founders sur scène insistent : tu ne débugges pas un agent, tu évalues. Construire une suite d'evals avant le premier client.

Heuristique : si ton equity de fondateur dépend de la qualité d'output de Claude, tu dois pouvoir mesurer cette qualité automatiquement, sans humain dans la boucle. Sinon tu vis dans le doute.

Pattern 2 · Vertical avant horizontal

Les startups gagnantes ont resserré sur un cas d'usage extrêmement précis. Eve Legal n'est pas « AI pour avocats » mais « analyse de risque sur renouvellements de contrats commerciaux M&A ». La précision du wedge permet :

  • Des evals fiables (le périmètre est borné)
  • Un prix premium (le client identifie son ROI)
  • Un système de prompts spécialisé (vs. tout-en-un)

Pattern 3 · Distribution avant feature

Plusieurs founders ont admis avoir passé plus de temps sur la distribution que sur le modèle. Avec Claude qui fait 80% du boulot d'ingénierie, la différenciation se fait sur l'accès au client, le canal, la marque.

We thought our moat was the prompt. It wasn't. It was the 12 months of distribution we built while everyone else was prompting. Founder, B2B AI startup (citation paraphrasée)

Judgement calls cités

DécisionLe piègeLe choix qui a marché
Open source vs. ferméVouloir capturer la valeur dès J1Open source la stack, fermer le workflow
Self-hosted vs. managedTout self-host pour « le contrôle »Démarrer managed, migrer si compliance le force

Riding the exponential curve

L'idée centrale (Dianne Penn keynote SF, reprise par Matt Bleifer « The Thinking Lever ») : les modèles continuent de s'améliorer. Choses qui ne marchaient pas il y a 6 mois marchent maintenant. Retry vos use cases échoués à chaque release.

Nuance honnête entendue plusieurs fois en off : personne ne sait combien de temps cette courbe tient. Mais coût marginal de re-tester un use case = quasi nul. Coût d'opportunité d'ignorer = énorme.

Comment « designer pour le prochain modèle » concrètement ?

  1. Construis avec évals avant features. Sans evals tu ne sauras pas quand le nouveau modèle débloque ton cas.
  2. Évite les workarounds prompt-engineering ultra-spécifiques. Ils créeront de la dette quand le modèle suivant n'en aura plus besoin.
  3. Architecture qui peut absorber un agent plus capable. Si demain l'agent peut faire la tâche en autonomie totale, ton produit est-il prêt à le laisser faire ?
  4. Garde une suite d'evals stable pour mesurer les sauts de capabilities, pas seulement la qualité courante.
The bottleneck moved from coding to everything around coding. Fiona Fung, Head of Eng Claude Code (Day 1 SF)

Boris exécute la démo avec l'app Claude Desktop. La tâche : ajouter les refunds au dashboard d'ACME. Contraintes annoncées en prompt :

Thariq Shihipar · « How we Claude Code »

Le pitch d'ouverture : les agents tournent désormais 8 à 10h. Ils coûtent du vrai argent. Quand ça part en vrille à mi-parcours, ça fait mal. Comment rester dans la boucle sans hover en permanence ?

Technique 1 · « Interview me »

The magic word for prompting is "interview me." Claude really gets that and starts to learn about you. Thariq Shihipar, Claude Code team

Dis ces mots et Claude passe en mode question. Pour quelque chose de vague, attends-toi à 30 à 40 questions sur plusieurs rounds. Démo originelle : « create a bill splitting app for me » (intentionnellement vague). Claude enchaîne : Qui est l'audience ? Colocataires ? Voyage en groupe ? Multi-devises ?

Sois honnête sur ce que tu ne sais pas. Utilise Claude comme thought partner pour extraire ce qui est dans ta tête, et faire émerger ce que t'avais pas pensé.

Technique 2 · HTML pour les plans (pas markdown)

I have totally stopped editing markdown files. I ask Claude to edit them. And if I'm asking Claude to edit it, there are prettier ways. HTML. It can include diagrams, code paths, mockups. Thariq Shihipar

Démo : 4 directions de design pour la bill-splitting app (receipt-style, ledger, Venmo-style, card-stack), chacune comme un set de fichiers HTML avec mockups full-screen. 15 minutes pour produire 4 directions. Fraction du coût en tokens.

Technique 3 · Verification (la partie qui compte le plus)

Given that agents are so good at writing code, the most important thing to focus on is verification. The most talented engineers on the Claude Code team are working on verification. Thariq Shihipar

Verification environments : comme Storybook, mais conçu pour la vérification. Sa démo React loadait les composants un par un, exécutait des actions, et enregistrait des video clips des résultats. Sur le codebase Claude Code, quand il soumet une PR, il reçoit une vidéo de Claude qui teste ses changements.

Modularize by verifiability. Structure ton code pour que chaque partie soit vérifiable indépendamment. Si tu peux vérifier la state logic séparément de l'UI, et render l'UI en isolation, tu as rendu tout le système plus trustworthy pour des agents.

Jarred Sumner · Robobun teardown

L'agent tourne en continu sur le repo Bun. Pour chaque issue ouverte :

  1. Reproduit le bug localement (lance du code dans un sandbox)
  2. Génère un test de régression qui échoue sur la version actuelle
  3. Tente un fix sur une branche
  4. N'ouvre une PR que si le test passe sur la branche fix

La PR vient de @robobun, est reviewée par @coderabbitai et @claude, puis demande l'approbation humaine pour merge.

Le filtre clé est l'étape 2 : il ne suffit pas de générer un fix plausible. Il faut prouver le bug par un test reproductible. Ça élimine 80% des PRs « cosmétiques » ou hallucinées.

1
Workshop · ~75min · Managed Agents

Ship your first managed agent

Du hello-world au premier déploiement. Squelette Python, outcomes rubric, sandbox config.

Pourquoi « managed » ?

Claude Managed Agents (public beta depuis le 8 avril 2026) est une couche au-dessus de l'API. Au lieu de tenir toi-même la boucle d'agent (prompts, tool calling, retry, memory, logs), tu déclares quoi et la plateforme gère comment.

Tu fournisLa plateforme gère
Un prompt systèmeBoucle d'inférence
La liste des tools (MCP)Tool calling, parsing, retry
Un rubric d'outcomes (optionnel)Grader, re-runs, scoring
Un sandbox config (optionnel)Exécution code, isolation
Une politique de mémoireStockage, retrieval, dreaming
python · claude-platform-sdk
from claude_platform import ManagedAgent, Tool

agent = ManagedAgent(
 name="support-triage",
 model="claude-sonnet-4-6",
 system_prompt="""You triage support tickets...""",
 tools=[
 Tool.mcp("zendesk"),
 Tool.mcp("notion"),
 Tool.bash(),
 ],
 memory="on", # auto memory + dreaming
 outcomes="./rubric.md", # succès défini en MD
 sandbox="vercel-functions", # self-hosted ok
)

result = agent.run("Ticket #5482: customer can't reset password")
Chiffre cité Day 1 : outcomes a lifté le success rate jusqu'à +10 points sur les benchmarks internes les plus durs (+8.4% sur docx, +10.1% sur pptx).

Give it memory

Les 3 niveaux : context window · memory store · dreaming. Heuristique YES/NO.

Stuffing your CLAUDE.md with every standard your team uses may feel like a good idea. You pay for it on every turn. The result is worse, more expensive performance. Daisy Hollman, Member of Technical Staff
Heuristique mémoire (Anthropic)
  • OUI · préférences de style de code projet
  • OUI · décisions architecturales et leur rationale
  • OUI · erreurs déjà commises (pour ne pas les répéter)
  • NON · données métier qui changent (à fetcher fresh)
  • NON · secrets / credentials (jamais)
3
Workshop · Evals

Write evals that move the score

Structure golden/edge/adversarial/regressions. Rubric.md + grader pattern.

La structure qui fonctionne
evals/
# evals/
├── golden_path/ # 20 cas réels typiques
├── edge_cases/ # 30 cas qui ont déjà cassé la prod
├── adversarial/ # 10 cas qui tentent prompt injection
├── regressions/ # tout bug fixé = nouvel eval ici
└── graders/ # prompts qui jugent les outputs
 ├── correctness.md
 ├── style.md
 └── safety.md
Rubric.md exemple
customer-support/rubric.md
# Customer support response · success criteria

A good response MUST:
1. Address the customer's actual question (not generic)
2. Cite the correct policy / KB article
3. Use the customer's name
4. Be under 200 words
5. Have a clear next action

A good response MUST NOT:
- Apologize more than once
- Use jargon (CTRL+F: "synergy", "leverage", "circle back")
- Promise something not in the KB
Heuristiques
  1. Chaque bug fixé en prod devient un eval. Pas négociable.
  2. Le grader doit être lisible par un humain.
  3. Score par catégorie, pas seulement moyenne.
  4. Ré-évalue à chaque release modèle.

5
Workshop · Live battle

Live agent battle

Compétition : correctness, coût, robustesse, observability. Patterns gagnants.

Format
  • Correctness · l'agent résout-il vraiment le problème (mesuré par evals fournies) ?
  • Coût · combien de tokens consommés ?
  • Robustesse · tient-il face à 5 cas adversariaux non vus ?
  • Observability · peut-on comprendre ce qui s'est passé en debug ?
Patterns qui gagnent (observation Anthropic)
  1. Démarrer simple · un seul agent, un seul tool. Itérer.
  2. Investir tôt dans les evals · pas après, pendant.
  3. Programmatic tool calling dès qu'un tool retourne > 1k tokens.
  4. Hooks pour corriger comportements observés (sans gonfler le prompt).
  5. Advisor strategy uniquement après que l'executor fonctionne seul.
Antipatterns observés : 4 MCPs avec 15 tools chacun = prompt majoritairement composé de schémas avant que l'agent ne lise une ligne du problème. Premium token waste.

08 · Thèmes transverses · 6 min

Ce qui revient partout.

Cinq idées clés qui structurent toute la journée et qui méritent d'être retenues séparément des annonces produit.

1 · Le context window reste une boîte

Les capabilities ont scalé énormément (raisonnement, tool use, durée d'exécution). Le context window non. ~1M tokens depuis > 1 an. Investir dans la gestion du contexte est l'une des skills à plus haut levier.

Schéma · Le context window comme contrainte fixe

2 · Le bottleneck a bougé

Écrire le code n'est plus la partie lente. C'est la review, la vérification, la coordination, et le « choisir quoi construire » qui sont devenus contraignants.

PRs hebdomadaires · équipe Noah Zweben · de ~500 à ~1150 en 5 mois

Conséquence : 1 seul engineer dédié à la doc → la doc devient le bottleneck → routines de doc-asynchrone overnight.

3 · Verification > code generation

Les modèles écrivent du code rapidement et plutôt bien. Ce qui distingue les équipes : leur capacité à vérifier l'output indépendamment. Structurer le code par vérifiabilité, pas par convenance mentale.

4 · Build for the next model

Refaire tourner les use cases qui ne marchaient pas il y a 6 mois. Garder une suite d'evals stable pour mesurer les sauts. Architecture qui peut absorber un agent plus capable demain.

▶ Matt Bleifer · The Thinking Lever · pourquoi retry vos use cases échoués à chaque release modèle

09 · Glossaire · searchable

Décoder le vocabulaire.

16 termes clés du CwC 2026. Filtre par mot-clé.

Routines
Sessions Claude Code déclenchées par cron, GitHub event ou API. Higher-order prompts asynchrones.
Dreaming
Process scheduled qui review les sessions et memory stores, extrait patterns, curate les mémoires. Research preview.
Outcomes
Rubric en MD lue par un grader indépendant qui score chaque output. L'agent retry avec le feedback.
MCP
Model Context Protocol. Standard ouvert pour exposer des tools à un LLM (DB, APIs, fichiers).
Advisor Strategy
Pair un petit executor (Haiku/Sonnet) avec un gros advisor (Opus) appelé uniquement sur les cas durs.
Compaction
Résume la conversation au seuil défini (suggéré 400k tokens). Sessions très longues sans mourir au mur.
Tool Search
Retrieve dynamique de tools. Évite de charger tout le schéma à chaque tour. Lovable : −10% tokens.
Auto Memory
Carnet local memory.md indexé. Reste sur la machine, jamais push GitHub.
Work Trees
Sessions Claude Code parallèles isolées sur le même repo. Sous-répertoire dédié par session.
Sandbox
Environnement isolé d'exécution. Self-hosted possible : Cloudflare / Daytona / Modal / Vercel.
Harness
Architecture multi-agent qui orchestre Planner / Generator / Evaluator pour les longues sessions.
Subagent
Agent spécialisé délégué par un lead agent. Contexte isolé, summary remonte seulement.
Hook
Code custom exécuté à des points précis (pre-tool, post-message). N'occupe le contexte que quand il tire.
Skill
Set de capabilities chargées à la demande. Préférable à un mega CLAUDE.md.
Eval
Cas de test pour mesurer la qualité d'un output. Golden path, edge cases, adversarial, regressions.
Grader
Prompt séparé qui évalue chaque output dans son propre contexte. Lisible par un humain.
